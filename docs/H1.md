# H1 evaluator checkpoint

The Pi extension is the model-facing boundary. Load it locally with:

```sh
pi --extension ./packages/arena-pi/extensions/arena.ts
```

The old ignored `.pi/mcp.json` is a P0 local configuration with a fixed
Strata path. It may start an additional Lean server in this checkout; the
extension-owned `arena-lean` server is the one selected dynamically by
`/arena`.

Select a theorem with `/arena Core.InitsUpdatesComm`, then use the v5 tools
described under "Harness v5" below: `arena_probe`, `arena_evaluate`,
`arena_profile`, `arena_idea`, `arena_candidate`, `arena_frontier`,
`arena_source`, `arena_declaration`, `arena_skill_read` and `arena_polish`.
The extension registers `lean-lsp-mcp==0.31.0` for the selected primary
environment. While a target is active, it blocks model Bash calls and edits
under `workspaces/`. Candidate files are written under temporary scratch;
the evaluator reconstructs source from the pinned Git object and never writes
to the worktree.

The reproduction adapter is:

```sh
uv run --no-project python -m tools.arena_eval Core.InitsUpdatesComm runs/baseline/Core_InitsUpdatesComm/arena-candidate-126.txt --mode full
```

## Current evidence

The pinned token utility reports 224 tokens for the reference, 124 for the
shortest local seed, and 126 for the transfer-safe seed. The reconstructed
126-token candidate compiles on v4.29.1, v4.27.0, and v4.26.0. The 124-token
seed compiles on the first two and fails on v4.26.0. The reference compiles
on the primary version. These checks use the three provisioned Strata
environments and a scratch file outside the workspaces.

Fast evaluation reports a local heartbeat count. Full evaluation also reports
`local_proxy`, calculated by the pinned Space's leaderboard scorer; `score`
remains null. With the wrapper recovered from the P0 scratch artifact, the
reference measured **4251 on three repeated runs**, matching the published
denominator. The 126-token proof measured 578 and produced a **76.72% local
proxy** with 3/3 compatibility. The earlier P0 4399 measurement has not been
explained; its generated reference file is no longer available. The pinned
Space publishes the denominator and leaderboard formula, but its worker
measurement procedure is not present in the pinned files. A server submission
of the 126-token proof and comparison with its per-problem result remain
mandatory before promoting an incumbent or treating a local combined score
as authoritative.

Full evaluations with a passing primary compile become session-local mutation
seeds, including partial transfers such as the 124-token 2/3 proof. No
submission incumbent is promoted yet.
The 124-token seed measured 543 primary heartbeats and a 66.18% local proxy;
its v4.26.0 failure is the older parser rejecting an applied theorem term in
`grind [...]`.

Environments resolve through `arena/environments.py` from a row's
(source, version, commit): an entry in `workspaces/registry.json`, else any
directory under `workspaces/` whose git HEAD is that commit. Standalone rows
(no repository file, such as PutnamBench) are rebuilt as their header plus the
candidate in `ArenaScratch/<name>.lean` inside the matching environment.
Corpus environments other than Strata still need H3 provisioning before use;
`python tools/arena_certify.py` reports which rows are provisioned and whether
each provisioned reference matches its published tokens, heartbeats and
compatibility.

## Budgeted non-interactive Pi sessions

`tools/run_pi_budgeted.py` starts one fresh Pi JSON-mode session for one
warm-up theorem. It generates a source-derived kickoff packet containing the
original reference proof and declaration signatures, selects `/arena`, saves
the Pi session and JSONL event stream, and writes `cost.json` on shutdown.
The agent can inspect pinned source with `arena_source` and
`arena_declaration`. Each evaluated proof is recorded under the run ID; its
reconstructed source stays available in a run-local shadow Lean project for
`lean_goal`, diagnostics, and `lean_multi_attempt`. The fixed project MCP
configuration is not loaded from this shadow working directory. Built-in
file/shell tools and context-file discovery remain disabled, so a fresh run
cannot read earlier local proofs. Supply a unique run ID:

```sh
uv run --no-project python tools/run_pi_budgeted.py \
  --model gpt-6-luna --theorem Core.InitsUpdatesComm \
  --run-id inits-luna-source-01 --hard-cap-usd 1 --dry-run
```

Remove `--dry-run` only when ready to make model requests. `--resume-run`
reopens the exact session and cost ledger after interruption. Use a separate
run ID and source-identical fresh session for `qwen3.8-flash` or
`deepseek-v4.1-flash`. An open-track submission also needs proof that the
specific weights and inference fit the Arena's 4×80 GB A100 and 48-hour limits.

The budgeted Pi model IDs include `arena-budget/gpt-6-luna`,
`arena-budget/qwen3.8-flash`, and `arena-budget/deepseek-v4.1-flash`. The
extension reads paid usage from all Pi
session entries, including abandoned branches, tool usage, cache warming,
compaction, and summaries. It prices the entries using OpenCode Go list rates:
GPT-6 Luna's low or high context tier for each request, Qwen3.8 Flash's
single tier, and DeepSeek V4.1 Flash's peak tier.
Before each provider request, the extension caps output at 16,000 tokens and
records an estimated exposure from the final provider payload. The estimate
is flushed for audit but does not count toward the cap. Returned usage is
priced and settled; a failed request without usage releases its estimate.
Unresolved requests from a previous process are released on exact resume and
remain visible in the journal. A request is denied only after observed usage
reaches the configured cap, which can be $0.10 through $3. This is an
**actual-usage stop**, not a strict spend guarantee: one in-flight response
can take observed spend over the cap, and a failed transport request may have
been billed by the provider without returning usage. Use a cap below the
competition maximum when that uncertainty matters. Unknown models and
changed model limits still fail closed.
The rates were checked against the published 2026-10-06 list; recheck them
before a later run because a price change alters observed spend.
The evaluator also returns spent and remaining budget to the agent. It returns
full Lean diagnostics for every checked version. Previous tool messages stay
stable to preserve prompt-cache reuse; old evaluations can also be retrieved
by candidate ID from the persistent ledger. The runner prints concise model,
tool, retry, and cost events while retaining the full JSON trace.

The run report shows both **ledger-priced observed tokens** and Pi's embedded
cost estimate. Luna costs $0.10 input, $0.50 output, $0.01 cache read, and
$0.125 cache write per million tokens while a request's billed prompt is at
most 272K tokens; a larger prompt costs $0.20/$0.75/$0.02/$0.25. Qwen3.8
Flash costs $0.15/$0.47/$0.016/$0.20. The UI screenshot rounds its $0.016
cache-read rate to $0.02. The old v3 ledger charged **every** Luna request at
the high tier, yielding **$0.201858** for 264 input, 71,807 output,
5,780,683 cache-read, and 129,347 cache-write tokens. Pi's embedded total
was **$0.109905**. Every v3 request had fewer than 272K prompt tokens, so
repricing the same usage at the correct tier reproduces Pi's total exactly.
Existing journals remain immutable; new runs use per-request tier selection.
Neither figure is a provider invoice.

### Candidate graph and live viewer

Each model candidate records its exact proof, parents, hypothesis and idea
label in the run ledger. All of these are optional metadata: a new candidate's
default parent is the candidate whose file is currently materialized, an
unknown parent or idea label is noted and ignored, and nothing is rejected
because of a schedule. Ideas are written only by the model (`arena_idea`).
`arena_frontier` is a compact status: best verified and fast-only candidates,
the model's ideas with attempts and last failure, and recent failures. An
advisory states a fact (for example that the last four candidates all descend
from `#5` without improving on it) and never blocks. The viewer lists ideas with
status and attempts. The merge worker is off unless the runner gets
`--merge-worker`; it competes with the model for Lean CPU and has produced no
real improvement.

To view an existing run live, start the loopback-only static-asset server:

```sh
python -m tools.serve_candidate_graph inits-luna-source-20261005-01 --port 8765
```

Open `http://127.0.0.1:8765/`. The page polls the run ledger every 2.5
seconds without losing its selected node or viewport. It shows the 2D DAG,
exact proofs, parent and base diffs, full diagnostics, scheduled idea lanes,
merge worker state, and score/token/heartbeat/cost charts. The cost chart
overlays Pi's embedded estimate when available. The server only exposes
the viewer assets and graph JSON. For a self-contained offline snapshot:

```sh
python -m tools.build_candidate_graph inits-luna-source-20261005-01
```

For an independent parallel $0.20 comparison, start these in four terminals
from the repository root. Each session has its own ledger, shadow project,
merge worker, and viewer; the two caps are per session, not a shared $0.20
total. Start each viewer after its runner has created the run directory:

```sh
python -m tools.run_pi_budgeted --model gpt-6-luna --theorem Core.InitsUpdatesComm --run-id inits-luna-v4-020-20261006-01 --hard-cap-usd 0.2
python -m tools.run_pi_budgeted --model qwen3.8-flash --theorem Core.InitsUpdatesComm --run-id inits-qwen38-v4-020-20261006-01 --hard-cap-usd 0.2
python -m tools.serve_candidate_graph inits-luna-v4-020-20261006-01 --port 8765
python -m tools.serve_candidate_graph inits-qwen38-v4-020-20261006-01 --port 8766
```

The budgeted runner uses `--no-extensions` and explicitly loads only Arena
and built-in MCP support. This excludes the Langfuse plugin in the user's Pi
settings; these runs have a local Pi JSON trace but no Pi-plugin Langfuse
audit. Load the plugin explicitly in a future runner revision if independent
remote reconciliation is required. Keep `runs/` private because traces
contain prompts, proofs, and tool output.

## Harness v5

`docs/SPEC-harness-v5.md` is the specification. Everything in it is implemented
and tested offline; the acceptance experiment (a $0.10 Luna/Qwen pair on
`Core.InitsUpdatesComm`) has not been run.

**Correct feedback.** Diagnostics are structured
`{severity, file_line, proof_line, column, message, source_line_text}`.
`file_line` is a line of the candidate file that `lean_goal` reads (the
heartbeat wrapper's 14 lines are subtracted in one function,
`engine.map_measured_line`). Only diagnostics inside the target declaration are
headlines; others are counted. The file is truncated after the target
declaration, and full compiler text is stored beside the ledger
(`full_diagnostics_ref`). `arena_probe` compiles drafts with `sorry` and returns
the goal at each tactic-position `sorry`; probes get `pN` ids, are restorable
with `arena_candidate`, can be promoted with `arena_evaluate from_probe`, and
are never scored or recorded as candidates.

**Metrics.** Every evaluation carries tokens, heartbeats, per-axis percentage
and contribution, the proxy (fast mode: an estimate labelled
`assumes_full_compat`), and deltas against the reference, the parent and the
best candidate. The packet states the exchange rates once.

**Profiler.** `arena_profile` (default: the current candidate) wraps every
tactic of the theorem's syntax tree in a heartbeat counter
(`arena/lean/profile.lean`) and reports heartbeats per proof line or block
(inclusive and self), share, nesting, top self costs with cumulative share, and
`profiled_total` against `measured_total`. It degrades to the outermost
tactics if instrumentation fails. The statement's own elaboration cost
(`statement_floor_hb`) is measured once per row.

**Skill and reasoning.** `packages/arena-pi/skills/arena-lean` is derived from
the vendored lean4 skill (`python tools/arena_skill.py sync`) and covers scoring,
token counting, heartbeat reasoning, compatibility pitfalls, immutability and
the tool workflow. Pi lists skills only when it has a read tool, so the
runner places the skill body in the system prompt and the model reads reference
files with `arena_skill_read`. `--thinking` (default `high`), `--no-skill`
and the skill's hash are recorded in `run-config.json`.

**Packet.** `arena/context.py` builds the kickoff packet from Lean elaboration
data (`arena/lean/context.lean`): goal before each top-level tactic, constants
the proof mentions with types and modules, definitions with constructors of
project types in the statement, earlier lemmas in the file, the reference
profile and the exchange rates. It is size-bounded, deterministic, cached under
`runs/cache/`, and contains no strategy text. `arena_declaration` falls back to
resolving names inside the theorem's own file.

**Cache and lifecycle.** The prefix (system prompt with skill, tool schemas,
packet) is static and history is append-only; dynamic values appear only in
new tool results and continuation messages. The extension records an alarm
when a warm request writes more cache than it reads, counts a continuation only
after a completed turn (provider errors back off and stop with `error_loop`),
bounds the last allowed request's output by the remaining cap, and reports
overshoot. SIGINT/SIGTERM stop Pi and still write `cost.json` and
`summary.json`/`summary.txt`. Compaction happens only past
`--compact-at-tokens` (default 200,000) through Pi's project settings; Pi
sends summarization requests straight to the provider, so the cost report
takes the larger of the ledger and the session's recorded usage.

**Comparing harness versions.** `tools/run_experiment_matrix.py` launches runs
that differ in one factor (`model`, `thinking` or `skill`) at a fixed
$0.10-$0.20 cap, checks that all runs saw the same packet, and writes
`matrix.json`/`matrix.txt` beside the run directories.

```sh
python tools/run_experiment_matrix.py --theorem Core.InitsUpdatesComm --prefix think-ab \
  --factor thinking --values medium,high --model gpt-6-luna --cap 0.1 --dry-run
```

**Optional polish.** `arena_polish` tries bounded mechanical variants of a
candidate (line deletions, `simp?` rewrites, closing-tactic substitutions) and
returns those that still compile and improve an axis, each as a probe. One
Lean job per run runs at a time, so polish never overlaps a model evaluation.
